Mission 2 · Split the crew

How the test works

One question, three ban lengths, real attackers, and every rule written down before the first one was caught.

The hypothesis

Banning an attacker for fail2ban's default 10 minutes does not lower the share who come back 12–24 hours after their first catch, compared with no ban, for attackers first caught between Thu 26 Nov 2026 2:00 PM and Fri 27 Nov 2026 3:00 PM IST.

Three crews

Flagsmith splits attackers 34 / 33 / 33 between three values of one flag, ban_policy. The value is the ban length in seconds.

No ban

Value 0. Caught, recorded, and let go. The baseline every ban is measured against.

10-minute ban

Value 600. fail2ban's default: banned on every server for 10 minutes, and again each time it is caught.

12-hour ban

Value 43200. Banned on every server for 12 hours, and again each time it is caught.

One attacker, start to finish

  1. CaughtFive failed SSH logins within ten minutes from one address on one server: fail2ban's own rule. The servers' password prompts can't be passed; every account is locked.
  2. AssignedThe controller asks Flagsmith for the attacker's ban_policy, once, using a keyed hash of the address as the identity. Flagsmith picks the arm and records the exposure.
  3. Banned everywhereThe ban goes to all 48 servers in 13 regions within seconds, through each server's firewall.
  4. Watched12 h 5 min after the first catch, when even the 12-hour ban has ended, the return window opens. It closes at 24 h 5 min.
  5. CountedIf the address reaches port 22 on any server inside its window, the controller sends came_back to Flagsmith, once.
  6. ComparedFlagsmith's results page compares the arms; an independent Beta-binomial calculation from the controller's own log checks it.

How Flagsmith is used

  • The flag holds the policy. ban_policy is a multivariate flag; its value is the ban length every server applies. Without Flagsmith, the servers don't know how long to ban.
  • The experiment does the split. Flagsmith assigns each attacker an arm and records the exposure; came_back is the metric (an occurrence, lower is better).
  • A kill switch. ban_enforce, read every 30 seconds: when it is off, nobody new is enrolled and no new ban is applied.
  • Ship the winner. When the experiment is complete, the winning value goes to everyone through the same flag: within 30 seconds every server bans each newly caught attacker for that length. Attackers already in the experiment keep their arm.

What counts

  • The result: the share of attackers who came back inside their window, per arm. Primary comparison: 10-minute ban against no ban.
  • The noise floor: the no-ban arm split in two by its identity (an A/A comparison).
  • Not in the result: attempts that reached SSH and knocks blocked during a ban. They show what a ban does mechanically, so they are reported apart.
  • Robustness: the same comparison with one unit per /24 network and per network operator, because one botnet can control many addresses.

Limits

  • Few attackers. About three were caught an hour on the first afternoon, so a small difference may stay out of reach. A tie is reported as a tie, with the size it can't rule out.
  • Botnets. Attackers are not independent: on the first afternoon, 5 of the first 11 came from one network operator. The per-network reruns are there for this.
  • Cloud servers only, for about 25 hours of enrolment. Home or office servers may see different attackers.
  • One shared address can hide several attackers, and one attacker can switch addresses.
  • Not tested: fail2ban's growing bans (bantime.increment) and its repeat-offender jail (recidive), the obvious next arms.
  • Servers added during the run (12, then 24, then 48), each noted in the pre-registration. The arms never changed.

Data and ethics

  • No address is stored or published. Each attacker is a keyed hash that can't be turned back into an address without the controller's secret key.
  • No password is recorded (the SSH server never logs them), and no username is shown anywhere.
  • Network operator and country come from an offline public-domain table (iptoasn.com).
  • The servers only defend themselves: they ban their own attackers and never reach back.
  • The data on this site is the published, anonymised export; it refuses to write anything that looks like an address.

Run it on your server

The repository's README has the setup steps: the settings, the command to start the controller, and what you should see when it works. With the kill switch ban_enforce off in your own Flagsmith environment, it only watches: nobody is enrolled and nobody is banned.
